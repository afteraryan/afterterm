# Phases: projects and threads

Execution plan for [`docs/design-02-projects-and-threads.md`](docs/design-02-projects-and-threads.md). One phase is finished and polished before the next goes deep. Each phase ships as its own release so the app is usable throughout.

Status values: `pending`, `in progress`, `implemented, untested by Aryan` (self-tested through the harness, not yet used by Aryan; Phase 7 onward, at his request on 2026-09-19), `done`. Dates are absolute. This file is the shared state for every session and agent working on the redesign: update the status table and the checklist as work happens, and add a dated line to the log at the bottom when a phase starts, finishes, or is handed to Aryan for testing.

## How this work is done

Agreed with Aryan on 2026-09-06.

**Orchestration.** Each phase is run by an orchestrator session that plans the phase, spawns subagents for independent pieces (renderer, main process, tests, docs), merges their work, and tests the result itself. The orchestrator comes back to Aryan only when the phase is finished and has passed its own testing, to hand it over for use. It does not ask Aryan to try half-built work.

**One worktree and branch per phase, chained.** Phases 0 and 1 (and 1.1) live together on `worktree-projects-and-threads-plan`; that is done and stays as it is. From Phase 2 on, each phase gets its own git worktree and branch, created from the previous phase's branch: Phase 2 branches from `worktree-projects-and-threads-plan`, Phase 3 from Phase 2's branch, Phase 4 from Phase 3's, and so on. Name them `phase-2-home-and-projects`, `phase-3-thread-identity`, and so on. A phase never commits to an earlier phase's branch, and nothing is merged to `main` until Aryan has tested and says so. Record the branch name in the phase's Log line.

**Self-testing, every phase.** Aryan tests nothing until every phase is done (decided 2026-09-07, see below), so the orchestrator's own testing is the only testing a phase gets. It has to be thorough enough that the finished app has no issues from the agent's side, main process or renderer, on the real session copy and on an empty profile. Before a phase is called done:
- Unit tests for everything with logic (data model, migration, detection, parsing), run and green.
- The app launched and driven by the agent on the **secondary monitor**, never on the primary where Aryan is working: every screen and interaction of the phase exercised, with screenshots captured. Phase 0 sets up the harness for this (see its checklist).
- The done-when line of the phase verified against the running app, not against the code.
- Every screenshot and every screen recording taken during that testing is saved under `docs/screenshots/<phase>/` in the repo and kept; nothing there is ever deleted (screenshots agreed 2026-09-07, recordings added the same day at Aryan's request during Phase 3).
- The app driven through the harness is recorded (`drive record start` / `record stop`, mp4 through CDP screencast and ffmpeg) for every flow that is exercised, so the run can be watched afterwards, not only read from screenshots.

**Testing by Aryan: once, after every phase is done.** Decided 2026-09-07 at the Phase 2 handoff. Aryan does no manual testing between phases, and no agent asks him to. When Phase 6 is finished he takes an unreleased production build (`npm run build`) as his primary afterterm for a few days, bugs go into `docs/bugs.md` tagged with the phase they belong to, the list is fixed, then a release is cut. The harness (`npm run harness -- --session <copy of session.json>`, a throwaway `AFTERTERM_USER_DATA_DIR` seeded from a copy of the real `session.json`, window on the secondary display, Claude session ids stripped by default) is the agent's tool, not Aryan's.

**How a phase ends.** One orchestrator session works on one phase only. When its phase is done and self-tested it comes back to Aryan with three things, in this order: the questions only Aryan can decide, the decisions it took on its own that he should know about, and, once that discussion is over, the handoff prompt for the next phase, pasted in the chat so a fresh session can start from it. It does not start the next phase itself.

Never close the running afterterm. A dev build runs beside it. A copied `session.json` carries Claude session ids; resume stays lazy (on click), so the two builds do not fight over a session unless the same thread is opened in both.

**Decisions taken on 2026-09-08 (Phase 6, by the orchestrator; Aryan sees them at the handoff).**
- PowerShell 7 and Windows PowerShell spawn with `-NoExit -EncodedCommand <bootstrap>`. The profile runs first, then the bootstrap captures the existing `prompt` function and wraps it: OSC 133;A, OSC 9;9 with `$PWD.ProviderPath` (file system paths only), `$?` put back with `Write-Error -ErrorAction Ignore` so a prompt that shows it still can, the original prompt, OSC 133;B. `-EncodedCommand` needs no execution policy, no quoting through node-pty's argv and prints no banner (all three verified on 7.6 and 5.1 before the phase started). If the bootstrap fails the shell stays open with the user's own prompt.
- Git Bash keeps `--login -i` exactly. The hook enters through the environment: `PROMPT_COMMAND` holds a one-line bootstrap that evals the hook text in `AFTERTERM_BASH_HOOK`. Verified: Git for Windows' `/etc/profile`, `/etc/bash.bashrc` and `profile.d` never set `PROMPT_COMMAND`, so the value survives the login sequence; starship and oh-my-posh prepend to an existing one. On its first run the hook replaces its own bootstrap fragment with `__afterterm_precmd` (keeping whatever the rc files added), un-exports both variables so child processes do not inherit them, reports the cwd as OSC 9;9 with the Windows path (`/d/x` converted by parameter expansion, other mounts through `pwd -W`, a builtin), and wraps the current `PS1` with the A and B marks, re-wrapping whenever PS1 changes. An rc file that assigns `PROMPT_COMMAND` outright discards the bootstrap and the integration is silently off for that shell; the opt-out covers the reverse case.
- WSL gets the same bash hook through `WSLENV` (appended to the user's own entries). Inside a distro the hook emits OSC 7 `file://<distro>/<path>`, with the distro name deliberately in the host slot. A new renderer OSC 7 handler turns `/mnt/c/x` into `C:\x` and anything else into `\\wsl$\<distro>\<path>`, and that Windows form is what `Tab.cwd` holds, so Explorer, the editor and the branch reader can use it. Spawning from a `\\wsl$\` cwd never stats the UNC path (a stat can block main and boot the distro); it becomes `wsl.exe -d <distro> --cd <linux path>`. A Windows cwd spawns as before (wsl.exe maps it to `/mnt`). zsh or fish inside the distro have no `PROMPT_COMMAND`, so the integration is off there. WSL is not installed on the development machine (`wsl.exe` is the store stub), so this path is covered by unit tests only and is flagged for Aryan.
- No OSC 133;C or D marks from any shell, the same as cmd: the renderer's state machine only needs A and B, and C or D would need a preexec hook (a DEBUG trap, a PSReadLine key handler), which is more invasive than the phase wants.
- Opt-out per shell in `prefs.json`: `shellIntegration: { cmd | pwsh | powershell | gitbash | wsl: "off" }`, read at every spawn, anything other than `"off"` meaning on. cmd is included for consistency even though its injection predates the phase. No settings UI.
- The cmd PROMPT injection moves out of `main.ts` into the same pure spawn planner as the other shells, so all five are unit-tested from one module and `pty:create` only applies a plan.
- No PowerShell startup banner is shown, matching VS Code's integrated terminal. Aryan rejected a hardcoded copy of the banner text on 2026-09-08 and decided afterterm's PowerShell threads should just open straight at the prompt instead, the same as VS Code's.
- Git Bash threads run MSYS's `ps -l` (about 110 ms) whenever the server watcher re-reads the process list and once before every Sleep, Close or quit kill, to bridge the parent links MSYS's exec breaks. No other shell pays this.
- The harness custom-prompt test uses a scratch home through `launch.mjs --env USERPROFILE=... --env HOME=...` (pwsh derives `$PROFILE` from the Documents folder, which expands `%USERPROFILE%`; Git Bash reads `~/.bash_profile` from `HOME`). Aryan's real profiles were never touched; oh-my-posh and starship are not installed on this machine, so the custom prompt was a hand-written `prompt` function and a hand-written `PS1` with an appended `PROMPT_COMMAND`.

## Phase 5: Servers

Goal: problem 1 from the original brief, a running server looks different and tells you its port.
