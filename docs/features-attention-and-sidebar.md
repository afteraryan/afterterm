# Attention and the sidebar: needs-you until answered, mark as unread, the rail, the panel

The full record of Phases 7 and 8 (`docs/design-03-sidebar-and-attention.md`), moved here from CLAUDE.md on 2026-09-20. Every paragraph is as it was written at the time; CLAUDE.md's "How the app works today" section is the short version.

### Attention state: needs-you until answered, mark as unread, one aggregate (Phase 7)

Before this phase, needs-you lied twice. `handleActivate` cleared a thread's `⚠` permission-prompt badge the instant the row was clicked, even though the prompt was still sitting there waiting for an answer: looking at a thread is not answering it, but the badge read as if it had been. And the spinner's re-arm rule, built for compaction, also applied to attention: arrowing through a permission prompt's own options is keystrokes that print to the screen, so that output re-armed `working` and dropped the needs-you badge on its own, again with nothing actually decided. Both bugs came from treating "the user looked" or "the screen changed" as if either meant "the user answered".

The state machine now, entirely in terms of what the thread was actually done to, not what it displayed: needs-you begins with the hook's `⚠` title, the same as before. It ends only three ways. First, the hook's own next title moving state on, `▶ working` from `UserPromptSubmit` or `✅` from `Stop` (`onTitle` in `spinnerState.ts`, unchanged from before this phase). Second, Enter pressed in that thread: at a permission prompt Enter is the answer (allow, or whatever option is highlighted), so `onAnswer` in `spinnerState.ts` flips attention to working; if Claude does not actually resume (the answer was "no" and the turn just ends), the ordinary silence-clear drops `working` again within its usual 2.5 seconds, so nothing is left spinning forever on a bad guess. Third, Esc or Ctrl+C in that thread: `onInterrupt` treats both as a real interrupt (Esc declines Claude Code's own prompt, Ctrl+C aborts the turn) and clears attention straight to quiet. Nothing else moves it: not viewing the thread, not arrow keys, not any other output. `onOutput` in `spinnerState.ts` still re-arms `compacting` back to `working` when output resumes after a quiet gap (compaction genuinely does finish silently and then resume), but it no longer re-arms `attention` for exactly the arrow-key reason above. `clearThreadBadges` in `app.tsx` keeps doing what it always did for the things that are genuinely "seen and done": it dismisses the overlay toast and clears `done` and `background` on view, and now also clears the unread mark on view; it simply no longer touches `attention`. One more rule from the handoff (Aryan, 2026-09-19): a `✅` that lands while the user is already looking at that thread, with the window focused (the same `activeTabId === tabId && document.hasFocus()` test that suppresses the toast), clears at once in `handleNotification`, since it has already been seen; with the app behind another window it stays done until the thread is looked at, the same as a background one.

The Enter signal itself is deliberately exact-match, not "contains a carriage return": `term.onData` in `Terminal/index.tsx` checks `data === '\r' || data === '\r\n'` for the answer, sitting right beside the pre-existing exact-match check for Esc (`'\x1b'`) and Ctrl+C (`'\x03'`) that already fires `onUserInput`. The same care that keeps that Esc/Ctrl+C check from misfiring on xterm's own focus-report escape sequences (`ESC [ O` / `ESC [ I` on tab blur/focus, which are multi-character and share the leading `ESC` byte) is why Enter is checked for equality rather than substring: a pasted block of text that happens to end in a newline is not a person pressing Enter and must not be read as an answer, and neither should any other multi-byte chunk that happens to carry a `\r` inside it.

Mark as unread is a separate, independent mark, not a variant of needs-you: it lives in the one thread menu (`threadMenu.tsx`'s `buildThreadMenu`), chats only ("Mark as unread" when clear, "Mark as read" while set, right after Sleep or Wake), since a shell has no conversation to flag as unlooked-at. It sets `Tab.unread` (persisted, `useTabState.ts`'s `setUnread`, no-op when the value would not change, `false` deletes the key rather than storing it so `sessionMigration.ts`'s `setUnreadFlag` can keep only a literal `true` on disk). It survives sleep on purpose: `sleepTab` in `sleepWake.ts` only ever deletes `notification`, never `unread`, because sleeping is a process going away and unread is a statement about the conversation, not the process. There is no toast for it, since the user just made the choice themselves and does not need telling. In `threadState`'s precedence (`threadView.ts`) unread sits above asleep, the one exception to "asleep wins over everything": a chat marked unread and then put to sleep still reads as `unread`, keeping its bell on a dimmed row, rather than falling back to a plain "Asleep · 2d" that would hide the mark. The header chip and the hover card's Status row both say "Unread" for it (`stateLabel`; the Status row was split out of Type on 2026-09-25), and `asleepSinceText`/the asleep pane are unaffected since a `threadState` of `unread` never reaches them, an unread asleep thread's chip reads "Unread", not "Asleep · 2d". It clears in `handleActivate` (opening the thread), from "Mark as read" in the menu, on the first real keystroke in that thread (`onTyped` in `Terminal/index.tsx`, fired for any `onData` chunk that does not start with ESC, so arrow keys and the focus reports xterm emits on a tab switch do not count; `handleTyped` in `app.tsx`), or on Wake (`wakeThread`), whichever comes first. The typing and waking rules were Aryan's at the handoff on 2026-09-19: marking the thread you are looking at unread lasts until you act on it.

`src/renderer/attention.ts` is new this phase and is now the one place every count in the app is computed: before it, `projectCounts` in `threadView.ts` and `homeTotals` in `homeView.ts` each summed a list of `ThreadState` by hand, and adding unread to "needs you" would have meant changing that rule in two places with no guarantee they stayed in step. `countStates` defines "waiting for you" once, as needs-you plus unread, matching design-03's phrase; `working` counts only the plain `'working'` state, not `compacting` or `background`, which is the same rule the play pill already followed before this module existed; the project pill still counts `working` and `running` together, unchanged. `countTabs`, `projectAttention` and `totalAttention` are the per-tab, per-project and grand-total wrappers `projectCounts` and `homeTotals` now call into instead of summing by hand. `railProjects`, `panelLists` and `firstThreadToOpen` are also built this phase, on the same foundation, but have no caller yet: they exist so Phase 8's rail and panel can read from the one aggregate from day one rather than a second implementation being written alongside them later.

The harness gained a `counts` reader (`drive.mjs`'s `cmdCounts`, reading `window.__afterterm.counts()` in `app.tsx`, itself built on `attention.ts`'s `totalAttention` and `projectAttention`): total and per-project waiting/working/running/finished, plus the rail's project list, so a test can assert the aggregate directly rather than counting bells in a screenshot. `drive.mjs`'s `sidebar` command prints a `[unread]` flag on a thread row alongside the existing `[asleep]` and `[x]`, read off the row's bell icon's `data-state="unread"` attribute.

**Verified in the harness on 2026-09-19.** On a Git Bash thread with the hook's own titles faked through `printf` OSC 0 sequences (see the test-method note below for why Git Bash specifically): needs-you survived switching away to another thread, a hover, clicking back in, arrow keys and typed text; it became Working the instant Enter landed in the thread, and quiet again once the silence window passed; it went straight to quiet on Esc and on Ctrl+C; a delayed `▶` title turned it Working and a delayed `✅` turned it Done, with `finished` reading 1 in `counts()` until the thread was viewed, which cleared it. On an empty profile, a real Claude Code session running in manual mode raised a real Bash tool permission prompt: it stayed Needs you through a round trip to another screen and back, a three-second look, and arrow keys through the prompt's own options; it went Working on Enter and Done at the end of the turn; it went quiet on Esc. The overlay toast fired for the same background prompt and was dismissed by clicking it, while the sidebar bell stayed exactly as design-03 says a toast dismissal and a badge clear are different things. A chat marked unread survived a graceful quit and relaunch of the same data directory and still carried the bell on reopen, clearing the moment the thread was opened; Mark as read from the menu cleared it without opening the thread at all. A seeded session with several projects gave a total `waiting` of 3 through `counts()`, with an archived project's own unread thread correctly excluded and a hand-edited `unread: "true"` (a string, not the literal boolean) correctly dropped, matching what Home's totals and the project pills showed on screen for the same session.

One test-method note worth recording: cmd.exe re-announces its own console title around every command it runs, so faking the `⚠` title with cmd's own `title` command puts the decorated title straight back the instant Enter is pressed, which looks exactly like needs-you failing to clear but is really cmd overwriting the fake before afterterm ever sees the real state change. That is a property of cmd's console title handling, not of afterterm's state machine: Claude Code's real hook sets the title once per event and leaves it alone, so a live Claude session never hits this. It is why the faked-title tests above used Git Bash, which does not re-announce its title on its own.

Limits: no change to toast timing or sound, both untouched by this phase; the rail and the panel are Phase 8, `railProjects`, `panelLists` and `firstThreadToOpen` exist but nothing calls them yet; `compacting` and `background` are still not counted as `working` anywhere, in `attention.ts` or in the older pill logic it replaced.

### The rail and the panel: Pinned, Recent, Other, project icons, search, the keyboard cycle (Phase 8)

The sidebar from Phase 1 put every project row, pinned or not, one behind the other in a single scroll, and the rail (Ctrl+Shift+B) was only that same list narrowed to icons. Phase 8 splits the two apart for good: a `Rail` component (`src/renderer/components/Rail/index.tsx`, `Rail.css`) that sits at the window's left edge on every screen, always shown, and a `SidePanel` (the same component and file, restructured) that lists only what is worth scrolling to, workspace-only, hideable on its own.

The rail is 76px wide, on Home, the workspace and the project page alike, so Home's and the project page's own 56px icon row (`ScreenNav.tsx`, now reduced to the bare `Screen` type) is gone; the rail carries the Home and Workspace icons everywhere instead. Top to bottom: the sidebar toggle (`IconPanel`, opens only while the panel is hidden on the workspace), the Home/Workspace pill (one vertical two-icon pill, background `#101010` against the rail's own `#171717`, a `#2a2a2a` highlight that slides between the two in 150ms with a slight overshoot, `cubic-bezier(.3,1.2,.4,1)`; the project page reads as Home in the pill, since it is a page visited from Home, one of the orchestrator's own calls below), Search and New thread (open the same way as the toggle, only while the panel is hidden), a thin separator, then one tile per project `attention.ts`'s `railProjects` names: a project with a thread waiting for you, one that finished and has not been viewed, or one that is compacting. A project with nothing pending is off the rail, pinned or not, current or not; nothing sits at the rail's own bottom. A tile shows the project's chosen icon (below) or the plain folder when none is set, on a faint tint of the project's colour; beside it, in a column, only the non-zero badges, top to bottom: waiting (amber), working (grey), finished (green), solid discs in muted gold, soft green and grey (`--badge-*` in theme.css, set B of the four shown to Aryan) with dark numbers, no movement (Aryan, 2026-09-19); compacting is not a count in that column but its own small purple disc with a dark glyph at the tile's top-left corner (`.tile .corner`, Aryan's decision at the Phase 8 handoff on 2026-09-19). Hovering the tile shows the project's name; hovering a badge shows what it is ("Waiting for you", "Working", "Finished") with no number, since the badge already carries one, and the corner icon says "Compacting". Both tooltips sit to the tile's right rather than underneath, because the rail sits at the window's own edge (`data-tip-side="right"` on `Tooltip.tsx`, which the rest of the app never needs). Clicking a tile opens the workspace on `attention.ts`'s `firstThreadToOpen`: the first thread waiting for you, else the first finished one, else the most recently active awake thread, else the project opens the way a Home card does (`openProjectFromRail` in `app.tsx`). Right-click gives the ordinary shared project menu, with no "New thread with shell" submenu, since that is a sidebar convenience rather than part of the shared menu.

The two closable blocks (the toggle above the pill, and Search/New thread below it) animate open and shut together with the panel: hiding the panel (the toggle or Ctrl+Shift+B) shuts the panel's width to zero over 320ms (`PANEL_SLIDE_MS` in `app.tsx`) while its own contents fade, and the rail's two blocks open to their height at the same time, their buttons fading in one after another, so the tiles glide down to make room; showing the panel again reverses both. Going from the workspace to Home slides the panel shut first (`goScreen`'s own timer, matching `PANEL_SLIDE_MS`) and only then changes the screen; coming back changes the screen at once and the panel slides open from zero, unless it was already hidden before Home, in which case it stays hidden and only the rail's blocks reopen. All of this is skipped outright under reduced motion, the same guard (`reducedMotion()`) the Phase 1.1 screen transitions use.

Project icons (`Group.icon`, optional, one of ten `PROJECT_ICON_IDS`: book, robot, bulb, globe, pen, film, house, music, bell, rocket) are picked in the New/Edit project dialog (`GroupModal`'s icon swatch grid, a folder swatch plus the ten `ProjectIcon` previews from `Icons.tsx`) and shown today only on the rail tile; the sidebar row, the Home cards and the project page keep the plain coloured folder, an open question below. `isProjectIconId` in `TabBar/types.ts` is the one validator; `sessionMigration.ts` calls it on load so an old id or a hand-edited string drops to the folder rather than rendering nothing or a bogus glyph.

The panel (`SidePanel/index.tsx`, its groups built by `panelView.ts`'s `panelSections`) lists, top to bottom: General (threads with no project, only when there are any), Pinned (a pin icon in the heading, the pinned projects in their dragged order, a thin line under the group) and Recent (unpinned projects with an awake thread or activity in the last three days, `attention.ts`'s `RECENT_WINDOW_MS`, sorted by `lastActiveAt` descending). There is no Projects section any more; every unpinned project that falls outside Recent sits in "Other projects · N", docked below the scroll, collapsed by default. Expanding it lists the rest as dim rows with no thread lists, each carrying its own relative activity time at the right ("1w"); clicking one brings it in (`onBringIn` in `SidePanel/index.tsx`, `bringProjectIn` in `useTabState.ts` and `app.tsx`): its `lastActiveAt` is stamped to now (forward only, so it can never look older than it did), it is expanded, and its first thread is selected, with nothing woken. This is a view filter over activity, not a pin: `Group.pinned` is never touched by any of it, and design-02's rule (pinning is explicit and only explicit) still holds. The Pinned and Recent headings each carry a collapse button at their right end (`IconCollapseAll`/`IconExpandAll`), which collapses or expands every project in that section in one `setGroupCollapsedMany` call rather than one `toggleGroupCollapse` per project; the Recent heading also carries the New project plus, right beside its own collapse button, since Recent is where a freshly created project first appears. The Recent heading always shows, even with nothing in it (it is where the plus lives), except while a search narrows the list (below), the orchestrator's own call: a bare "Recent" heading with the plus is still useful, but a search result with an empty heading and a plus that creates something outside the search is not.

The Search box (`SidePanel`'s `.srch`, `panelView.ts`'s `filterPanel`) filters the panel in place: a case-insensitive substring match over project and thread names, a project whose own name matches keeps every one of its threads, otherwise only its matching threads show and a project left with none drops out entirely; no match anywhere reads "No matches". While there is text, New thread and the docked Other projects row both hide, since neither means anything mid-search. Escape empties the box when it has text, and blurs it (hands the keyboard back) when it is already empty, so a second Escape always does something new. Ctrl+Shift+P still opens the palette, the only place a closed thread is found by name.

Ctrl+Shift+Down and Ctrl+Shift+Up (`main.ts`'s `before-input-event`, dispatching `next-thread`/`prev-thread` beside the existing shortcuts) move through every thread row the panel is actually showing, in panel order, across projects: from one project's last row straight into the next project's first, skipping a collapsed project and any row folded behind "Show N more", wrapping at either end. The row order itself is `panelView.ts`'s `visibleThreadIds` (General, then each Pinned project, then each Recent project, each folded through `threadView.ts`'s `foldThreads` with `attention.ts`'s `isWaitingState`; Other contributes nothing, since it holds no thread lists to cycle through), and `cycleThreadId` picks the next or previous id in that flat list. `app.tsx`'s `cycleThread` asks the mounted `SidePanel`'s own `cycleThread` (exposed on `SidePanelHandle`, since only the panel knows its own fold state and search text) and activates the result with `activateTab`'s new `keepProjectOrder` flag set to true. That flag exists because of a bug the self-test found: activating a thread ordinarily stamps its project's `lastActiveAt`, which is exactly what orders Recent, so the cycle landing in a project would instantly send that project to the top of the list it is walking, and two projects would trade first place under the keys forever rather than the cycle ever reaching a third. `keepProjectOrder` skips only that project stamp; the thread itself is still stamped, and an ordinary click or typing in a thread still raises its project the way it always did.

Compacting (`⚙`) is its own state from this phase, not a second reading of the working spinner: `StateIcon`'s `'compacting'` case now renders `IconCompact` (three lines pressing into one) at its own colour (`--compact: #60a5fa` in `theme.css`) rather than the grey spinner, on the sidebar row, the header chip and the hover card (`stateLabel` already read "Compacting"; since 2026-09-25 on its own Status row); a project with a compacting chat appears on the rail with the compacting icon on its tile's top-left corner (no number); `attention.ts`'s `countStates` gains a `compacting` bucket, counted nowhere else, so the project row's play pill still counts only working and running, exactly as the Phase 7 handoff decided.

The five-row fold (`threadView.ts`'s `foldThreads`) gained an `isWaiting` parameter this phase: every caller in the panel now passes `t => isWaitingState(threadState(t))`, so a hidden row behind "Show N more" that is needs-you or unread forces that project's list open, the same as the active thread already did. This closes the bug logged after the Phase 7 self-test (`docs/bugs.md`, now removed): a needs-you row could fall behind the fold the moment the active thread moved back inside it.

`ui.panelHidden`, a new optional top-level object in `session.json` (`sessionMigration.ts`'s `asUi`, `SavedSession.ui`), is the only new persisted field this phase: per-project collapse stays `Group.collapsed`, and the Other-projects fold and the search text are both transient, cleared on every launch, since neither is a setting worth remembering. It is written by the ordinary 2-second debounced save and, since a bug the self-test found, by the synchronous `beforeunload` flush too: that flush calls `serializeSession` directly rather than through the debounced path, and its first cut left `ui` out, so a hidden panel came back shown after a graceful quit; the flush now passes `{ panelHidden: panelHiddenRef.current }` the same as the debounced save does.

The harness gained three readers and one action for all of this: `rail` (`drive.mjs`'s `cmdRail`, reading the rail's screen, whether its two blocks are open, which side of the Home/Workspace pill is selected, and each tile's name and badges), `dock` (the panel's docked "Other projects · N" row on its own, also folded into `sidebar`'s own output now that the panel has General/Pinned/Recent/Other instead of General/Pinned/Projects), and `search` (with text, clicks and sets the Search box the React-friendly way; with none, reports its value and whether New thread and the dock are currently hidden by it). `counts` (Phase 7) now reports `compacting` alongside waiting, working, running and finished. `window.__afterterm` gained `group(id)` (a project's own live record) and `panelOrder()` (the panel's own `visibleIds()`, the exact list the keyboard cycle walks), alongside the existing `tab(id)` and `counts()`. One harness lesson from the self-test: Vite's Fast Refresh keeps a mount-only effect's stale closure alive across a hot-reloaded edit, so after the `keepProjectOrder` fix landed the shortcut dispatch kept calling the previous `activateTab` until the page was actually reloaded; `drive.mjs` gained a `reload` command (`cmdReload`, `location.reload()` through `eval`) for exactly this.

Limits: the rail lists a project only for a thread waiting, finished or compacting, nothing else, so a project with only a running server (no notification pending) is never on it; the docked Other list carries project rows only, no thread lists, so it plays no part in the keyboard cycle; the cycle skips a collapsed project and any fold-hidden row by design, the same as clicking one would need to expand it first before reaching what is inside.

### Small fixes from manual testing (2026-09-25)

**No Open item, and the header's own menu.** `threadMenu.tsx` now has two builders over shared item helpers: `buildThreadMenu` for the row menu (the sidebar right-click and the project page rows) and `buildHeaderMenu` for the header's dots button. Neither has Open (Aryan, 2026-09-21: a click on a row already opens its thread, and the header's thread is the open one), so `ThreadMenuActions.open` is gone. The header's menu leaves out the Open in <editor> entries, since the editor button sits beside the dots; its type is `HeaderMenuActions`, `ThreadMenuActions` without `openInEditor`.

**New threads first.** `insertNewThread` in `threadView.ts` puts a new thread (addTab) and a thread resumed from History (resumeFromHistory) before its project's first thread, so the five-row fold shows the newest threads and the old ones go behind "Show more". A project's threads stay contiguous; a project with no threads, or a thread in General, still goes at the end. The panel shows a project's threads in tab order and sorts nothing, so this is the whole change; Ctrl+Tab's session order follows it.

**Bringing an opened project into view.** `SidePanelHandle.revealProject(groupId)` is called by `app.tsx` after `projectActions.open` (Home cards and rows, the palette, the project page's Open, the project menu's Open), after a rail tile click and after `bringProjectIn` (the Other projects drawer). It clears a search that is narrowing the list, closes the drawer, then waits `REVEAL_SETTLE_MS` (260ms, the project's expand transition) and retries every 50ms while the workspace is still hidden (opened from Home it is `display: none` until the screen switches). It measures the project row down to its active thread row (`.th.sel`) and scrolls by `revealScrollTop` in `panelView.ts`: nothing when the region is already in view, otherwise the smallest move with 8px of air, a region taller than the view aligned to its top, and a stop within 48px of the start snapped to 0 so the first section heading is not left cut off (seen in the harness: a stop at 18px hid half of "Pinned"). Smooth, or instant under reduced motion. The row then takes `.revealed` for `REVEAL_FLASH_MS` (1.2s): a one-off `pj-reveal` animation from `--hover2` back to transparent, and a plain `--hover2` background under reduced motion, since a highlight is not movement. A slow `transition` on the row was tried first and dropped before testing: it would have slowed every ordinary hover too.

**Found in the self-test: Enter in the palette woke the thread it opened.** The palette's Enter handler did not call `preventDefault`. Opening a project whose last thread was asleep mounted the asleep pane, whose Wake button takes focus, while the key press was still being handled, and its default action pressed Wake. The palette now stops the key press once it has used it; the same flow in the harness then left the thread asleep.

**The project pills show what the thread rows show (2026-09-25).** Aryan's screenshots: afterterm showed "▶ 1" while one of its chats had the spinner, and Revy App showed the same "▶ 1" for a thread running a server. `projectCounts` had returned `running: working + running`. It now returns `{ needsYou, working, running, compacting }` through `pillCounts` (also used by `homeTotals`): `working` is the working state plus background, since `StateIcon` draws the same spinner for both, and `running` is servers only. `countStates` gained a `background` bucket for this; the rail's badges do not read it, so a thread only running background tasks still puts no badge on its tile, as before. The project row (`SidePanel`) and Home's cards, rows and totals draw a spinner pill (`.sig.work`, the 11px spinner) and the play pill (`.sig.run`) each when above zero.

**Background tasks get the hourglass (2026-09-25, PR #40).** After the fix for a viewed thread that kept "Background tasks" (PR #39), Aryan chose option 2 of three: background stops sharing the working spinner. `StateIcon` draws `background` as `IconHourglass` (`.si.bg`, `--text2`, the same glyph the toast already used) on the row, the header chip, the hover card and the project page; `pillCounts` returns `background` apart from `working`, and the project row and Home's cards, rows and totals draw an hourglass pill (`.sig.bg`) beside the spinner pill. The rail still ignores background. The hourglass flips: a half turn in 0.7s on `cubic-bezier(.22, 1, .36, 1)` (fast start, slow stop), a 0.8s rest, the next half turn (`@keyframes hourglass-flip` in `theme.css`, 3s per two flips; the first rest was 1.6s and Aryan asked for it shorter). Off under reduced motion through the global rule. Sampled in the harness every 50ms: 60° at 50ms into a flip, 148° at 200ms, 179° at 500ms, then still until the next. `drive sidebar` and `drive home` print `bg=`.

**One sidebar toggle, fixed on the rail (2026-09-25).** The rail's toggle lived in the first `.railblk`, which only opened while the panel was hidden; with the panel open it collapsed and the Home/Workspace pill slid up into its place, so a second click on the same spot opened Home (Aryan's entry). The toggle is now a plain `.ic` button (`.rail-toggle`, `data-toggle-panel`) before the pill, on every screen, its tip reading Close sidebar or Open sidebar. On the workspace it calls `togglePanel`; on Home and the project page, which have no panel, it clears `panelShut` and `panelHidden` and goes to the workspace. The panel's `.brand` row (its own toggle) and the `onToggleCollapse` prop are gone, and `.side-body` gets 8px of top padding so Search starts level with the rail's first button. The second `.railblk` (Search and New thread while the panel is hidden) is unchanged; it sits below the pill, so it moves nothing above it.
