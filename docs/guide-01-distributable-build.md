# Guide — Shrinking the build into a shareable self-extracting `.exe`

`npm run build` produces `out\afterterm-win32-x64\` (~346 MB on disk: Chromium + node_modules).
That's fine to run locally, but too heavy to hand to someone. This guide turns it into a
single **~67 MB self-extracting `.exe`** (`afterterm-setup.exe`) — roughly half the size of a
plain `.zip` of the same folder — that recipients just double-click to unpack. No unzip tool
required on their end.

The savings come from two independent levers:

1. **Pruning dead weight** from the build folder (safe — all reproducible by `npm run build`).
2. **LZMA2 ultra compression** via 7-Zip instead of `Compress-Archive`'s weak zip/Deflate.

For reference, the same build folder compressed three ways:

| Method | Size | Recipient experience |
|---|---|---|
| `Compress-Archive` (zip/Deflate) | ~122 MB | Built-in, double-click |
| 7-Zip `.7z` (LZMA2 ultra) | ~67 MB | Needs 7-Zip / WinRAR |
| **7-Zip self-extracting `.exe`** | **~67 MB** | **Double-click, no tools** |

The SFX wrapper costs only ~0.2 MB over the plain `.7z`, so it's the default choice for sharing.

---

## Prerequisites

7-Zip (the compressor — `Compress-Archive` cannot produce LZMA2 or SFX):

```powershell
winget install --id 7zip.7zip -e --source winget --accept-source-agreements --accept-package-agreements
```

> Pin `--source winget`. The default `msstore` source can fail on this machine with a
> certificate error (`0x8a15005e : The server certificate did not match...`).

Installs to `C:\Program Files\7-Zip\` (`7z.exe` + the `7z.sfx` GUI extractor module).

---

## Step 1 — Build, then prune dead weight

```powershell
npm run build   # produces out\afterterm-win32-x64\
```

Then strip files that are never needed at runtime. **All of this is regenerated by the next
`npm run build`, so it's non-destructive in practice.**

```powershell
$base = "D:\Tinkering\afterterm\out\afterterm-win32-x64"

# (a) Debug symbols — ~53 MB, never loaded at runtime
Get-ChildItem $base -Recurse -Include *.pdb | Remove-Item -Force

# (b) Wrong-arch node-pty prebuilds — this is an x64 build, arm64 binaries are inert
Remove-Item "$base\resources\app\node_modules\node-pty\prebuilds\win32-arm64" -Recurse -Force

# (c) Non-English Electron locale packs — ~41 MB; keep only en-US.pak
Get-ChildItem "$base\locales" -File | Where-Object { $_.Name -ne 'en-US.pak' } | Remove-Item -Force
```

> **Locale caveat:** stripping `locales\` to `en-US.pak` only is safe when every recipient runs
> an English Windows. On a non-English locale, some Electron versions can fail to start or show
> blank UI because the matching `.pak` is missing. If you're distributing to unknown machines,
> **skip step (c)** — it costs ~40 MB but removes that risk. Steps (a) and (b) are always safe.

---

## Step 2 — Pack into a self-extracting `.exe`

```powershell
$7z   = "C:\Program Files\7-Zip\7z.exe"
$base = "D:\Tinkering\afterterm\out\afterterm-win32-x64"
$sfx  = "D:\Tinkering\afterterm\out\afterterm-setup.exe"

if (Test-Path $sfx) { Remove-Item $sfx -Force }
& $7z a "-sfxC:\Program Files\7-Zip\7z.sfx" -t7z -m0=lzma2 -mx=9 -md=64m -mfb=64 -ms=on "$sfx" "$base"
```

Flag notes:
- `-sfx<full path to 7z.sfx>` — prepends the GUI self-extractor stub. **Use the full path** to
  the module; the bare `-sfx7z.sfx` form fails with *"cannot find specified SFX module"*.
- `-m0=lzma2 -mx=9` — LZMA2 at ultra. This is what beats zip on the ~192 MB `afterterm.exe`.
- `-md=64m` — 64 MB dictionary (bigger = better ratio, more RAM at compress time).
- `-mfb=64 -ms=on` — fat word size + solid archive (treat all files as one stream).

For a plain archive instead of an SFX, drop the `-sfx...` flag and use a `.7z` output path.

---

## Result

`out\afterterm-setup.exe` (~67 MB). Recipients double-click → choose a folder → run
`afterterm.exe` from inside the extracted `afterterm-win32-x64\`.

**SmartScreen note:** the SFX is unsigned, so recipients may see a Windows "unknown publisher"
warning — *More info → Run anyway*. If that friction matters, ship the plain `.7z` instead
(identical size, no warning, but they need 7-Zip/WinRAR to open it).

---

## Updating an existing install on another machine

afterterm is **portable** — there's no Windows installer, just an extracted
`afterterm-win32-x64\` folder you run `afterterm.exe` from. "Updating" = replacing
that folder with a newer build. **User data is preserved automatically**: tabs,
groups, `prefs.json`, and `session.json` all live in `%APPDATA%\afterterm\`,
separate from the app folder, so a folder swap never loses them.

On the target machine:

1. **Close all afterterm windows** — Windows locks a running `.exe`, so the old
   folder can't be overwritten while afterterm is running (same reason the build
   machine must not run afterterm from its build folder).
2. **Run the new `afterterm-setup.exe`** (*More info → Run anyway* past SmartScreen).
3. **Extract**, either:
   - to a *new* empty folder, then delete the old `afterterm-win32-x64\`, or
   - to the *same parent folder* to overwrite in place (**Yes to All** on prompts).
4. **Run `afterterm.exe`** from the new folder; repoint any shortcut/taskbar pin
   if the path changed.

First launch of the new build runs the notifier self-install
(`claude-hook-install.ts`) — so an old build that predated notifications will,
on this update, register the hook and show the one-time "Claude Code
notifications enabled" toast. (Needs Claude Code + `pwsh` present on that
machine; see `docs/ideas.md` → *Dependency check on first launch*.)
